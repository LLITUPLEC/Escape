# Durable recovery: entries, outcomes and achievement delivery

These are server-only primitives. They expose no client-supplied winner/refund RPC. Integration hooks in the main match module are owned by the coordinating change; local fault tests alone do not prove the production hooks or deployment.

## Storage and state transitions

| Collection / key | State | Atomic boundary / retention |
|---|---|---|
| `duel_race_entry/active`, `run:<result_id>` under user | `pending → bound → settled` or `refunded` | Existing immutable costs retained. Claim records actual `match_id`, all human owners and players. A `finish_intent` freezes winner/draw and reward policy before settlement. Wallets, settled receipts and per-user stats outboxes commit together. Keep bound/intents; terminal timestamps `settled_at` / `refunded_at`. Never delete the active receipt's target. |
| `duel_pve_entry/active`, `launch:<token>` under user | `reserved → bound → consumed`; abandoned launch `→ refund_pending → refunded` | Debit + token are one batch; bind is CAS before match-create return. Consume is done at successful server start, and is also available as pure writes in an outcome transaction. Refund + receipt + profile + journal abort marker share a batch. Preserve active and `refunds` index, all nonterminal/credit records. Terminal `consumed_at` / `refunded_at`. |
| `duel_match3_journal/result:<id>` under user | `prepared → committed → complete`, or terminal `aborted` | Frozen plan persists before any economic grant. Builder returns fresh profile/sheet CAS writes; reward receipt and committed marker are in the same transaction. Achievement/stat increment and complete marker share another transaction. Preserve prepared/committed records and their indexes. Terminal `completed_at`. |
| `duel_match3_journal/pending` | Map of unresolved result IDs | Updated atomically with creation/completion. Bounded at 128; refuses a new intent instead of truncating an earned reward. |
| `duel_match3_journal/retention_v2` | Issued sequence, unresolved admissions, retired watermark and latest four completion receipts | Server-issued sequence/nonce admits a new result before battle settlement. Closing a ticket and its economic/stat transaction share CAS. Unfinished tickets and compacted ranges preserve deduplication after old result rows are removed. |
| `duel_pve_entry/refunds` | Tokens with remaining energy refund credit | Energy which does not fit below the cap is not discarded or repeatedly credited. The remainder stays in the receipt/index until space is available. This is separate from inventory pending loot. |

All service receipts/indexes have `permission_read=0`, `permission_write=0`. Public stats/profile retain their existing read permissions. A builder cannot add unversioned/cross-user/journal writes. Inventory overflow stays in the character sheet's existing pending-loot mechanism, not a second recovery item queue.

## Recovery policy

`duel_match3_recovery.new({...}).maybe_recover(uid,{force=true,limit=8})` processes journal → Race → PvE → newly created effects. It can be called from trusted login/resource-read hooks and bounded maintenance for offline users. Failed attempts remain retryable and are not throttled. A successful VM-local read throttle lasts five seconds and is not a durability mechanism. Reentrant calls do not recursively restart recovery.

An active bound Race is never refunded on elapsed time alone. A recorded authoritative match ID must be proved absent with `match_get`; probe exceptions fail closed. A persisted finish intent takes precedence and replays the frozen settlement. Without an intent, a proved orphan refunds every human's recorded costs atomically and does not fabricate a win, XP or prize. Normal human winner remains **4 matter**, bot outcomes return the actual immutable fee with the pre-existing XP policy, and repeated finish/cancel/recovery cannot duplicate funds.

Old bound Race receipts lacked `match_id`. They can only be auto-recovered after a proved empty global authoritative match list; with any running match or a failed probe, they remain protected (`legacy_race_match_unknown`). An idle deployment/migration sweep is the safe recovery opportunity. Old failed PvE debits without any reservation receipt cannot be reconstructed reliably and are not refunded by guessing the current price.

PvE reserves its normalized recorded cost before create. A reserved token expires after 90 seconds; binding an expired/refunded token is rejected. A bound unstarted orphan is refunded; a consumed played match is not. A prepared reward journal blocks neutral refund, and a refund creates a create-only abort marker on the same PvE result key. This prevents the check-then-refund/free-victory race.

Supported launch reservation costs are energy, gold, ore, matter and existing key counters. Item-backed ingots are deliberately rejected until spending them is integrated with a joint inventory transaction; a scalar debit must not diverge from item stacks. Duplicate cost lines are summed before affordability checks.

## Bounded deduplication and automatic retention (0.3.13)

`duel_match3_stats/summary.match_result_ids` keeps the latest **four IDs**. The authoritative reader normalizes an existing 64-ID summary to four with CAS; normal writes retain the prior three and append the completed result. Lifetime totals, mode totals and achievements remain in the summary. The four IDs are a small recent cache, not the permanent replay protection.

Normal authoritative match admission issues a protected sequence/nonce ticket for each result channel. `retention_v2` keeps a monotonic sequence, a retired watermark, closed ranges around unresolved holes, and the latest **four completed or aborted result receipts per player across modes**. Completion order is the successful CAS order, so a late older match can finish after a newer one. Closing the ticket, updating recent completion metadata and granting the final economic/stat effect share one atomic batch. A missing result must present its original open ticket; an evicted result's old ticket returns `result_compacted` and cannot create a new award. Result retries only look up their existing ticket and never issue a replacement. Tickets are server-only, not a client-supplied UUID admission API.

Post-commit cleanup best-effort removes evicted completed rows. A delete failure leaves the award committed and maintenance retries later. Therefore four is the completed-history target, not an assertion that the whole collection always contains four rows: the protected control and pending indexes remain, unfinished earned results are retained, and a temporary cleanup backlog can exist. At most 128 unresolved admissions are accepted; a new battle is refused rather than dropping unresolved work. Unused channels are retired on terminal completion. An offline sweep retires an old admission only after the authoritative match is proved absent and there is no result/pending reference or frozen Race finish intent. Probe errors preserve it.

`duel_storage_maintenance.lua` only considers versioned, server-protected, terminal Journal rows absent from `pending`. Journal compaction no longer waits 30 days. Genuine legacy prepared/committed rows are adopted only when the durable row and pending index both exist. Missing legacy UUIDs cannot begin a fresh reward. Legacy completed rows are reduced to four by their recorded completion timestamp; their old timestamp has only one-second precision, so ties use a deterministic ID order. The new protocol's completions outrank pre-upgrade records. Terminal Race/PvE entry receipts still require **30 days** and exact terminal proof; active/latest targets and unfinished recovery/refund work remain protected. Finished tournaments require terminal reward proof. Inactive rate-limit buckets retain their separate seven-day policy. This cleanup does not delete player totals, inventory, achievements or an unfinished earned reward. Boss attempts/mail and shop purchases use their own admission/claim CAS and are outside this Journal cleanup.

The 0.3.12 scheduler uses the authenticated RPC maintenance hook, a shared CAS lease and a **60-second** next-run interval. It scans **100 rows per page**, with at most **10 pages across all five collections per run**. A **250 ms** wall-clock budget is checked between pages; an individual database call or recovery operation can exceed it, so this is not a hard total latency promise. Per-collection cursors and the next round-robin collection are persisted. Empty/exhausted collections are visited only once in that run. Startup recovery still scans bounded first pages and attempts at most 50 distinct owners; regular maintenance attempts recovery for at most two owners per run.

This is traffic-triggered maintenance, not an operating-system cron job. The VM-local minute throttle avoids redundant checks; the shared lease prevents multiple runtime VMs from running the same pass. With no traffic there is no new gameplay journal growth. `duel_storage_maintenance/v1.last` records actual pages, scanned/deleted rows, elapsed milliseconds, configured budgets, recovery attempts and conflicting delete batches. Watch measured cursor progress and latency when sizing a deployment; the configured maximum of 1,000 scanned rows per minute is not a production throughput benchmark. The former 50-row/hour-per-collection scan could not keep pace with a target of 30,000 new result receipts per day.

Under the previous 0.3.12 policy, 30,000 new result receipts/day and 30-day retention implied roughly **900,000 completed result receipts** before scan lag. The 0.3.13 target instead scales with four completed receipts per participating player, plus protected metadata, unfinished work and any deletion backlog. No million-row latency/load test was performed. The historical read-only production snapshot on **2026-10-26 16:35:57 UTC** contained **500 Storage rows**, **1,310,720 bytes** of Storage relation space including indexes/TOAST, and **326 complete result receipts** occupying **216,211 JSONB bytes**. No journal row was over 30 days old; both sampled summaries then had exactly 64 IDs. These are measurements before the new migration, not its resulting size or a throughput claim. Evidence and exact query remain in `Design/Release-0.3.12/validation/{production-storage-aggregates.json,storage-audit.json,storage-audit-aggregates.sql}`; that audit performed no production deletion.

## Journal API

- `issue_many(specs)` admits trusted fresh authoritative battle channels before settlement; each spec supplies `uid`, `id`, `kind` and origin. Its returned tickets must remain attached to that admitted action.
- `ticket(uid,id)` only returns an already issued open/recent ticket. It never admits a missing UUID. `cancel_unused_many(specs)` retires channels without a result or pending reference.
- `prepare(uid,id,kind,plan,ticket)` writes one immutable server intent under an issued ticket. Repeating the same plan is idempotent; changing a frozen plan returns `result_plan_conflict`.
- `prepare_writes(...)` returns the equivalent pure CAS writes, for an existing atomic parent transaction such as Race settlement.
- `commit(uid,id,builder)` passes a copy of the plan to `builder(plan)`; it returns fresh CAS writes and a receipt. The journal appends its committed marker in the same `storage_write`. A replay returns the stored receipt without re-running the builder.
- `deliver_effects(uid,id)` atomically increments `achievement_deltas` / optional `match_stats` and marks completion. A DB error leaves an outbox entry, not a second currency grant or lost progress.
- `recover(uid,handlers,limit)` rebuilds prepared economic intents with trusted kind handlers, then drains committed effects. Missing handlers preserve the intent and return pending.
- `abort_writes(uid,id,reason,ticket)` returns protected abort/control writes for a proved refund's same transaction. It refuses a key already owned by a reward intent. A legacy refund may create a terminal-only no-grant marker even when the unresolved-admission quota is full.

Consumable activation uses its own protected sheet ledger (`use_ledger.last_seq` and four recent receipts), because it is an explicit inventory action rather than a battle outcome. Status returns `next_use_seq`; the client keeps the same request ID, sequence, item and index across an uncertain acknowledgement. An old evicted sequence cannot decrement inventory again. Consumable binding to an ordinary battle still uses its pre-issued battle Journal ticket; a boss binding is persisted with the boss attempt snapshot.

Normal PvE uses `state.stats_result_id..":pve"`; Race stats use `..":stats"`. A plan's `match_stats.result_id` keeps compatibility with the existing authoritative summary deduplication. Root's managed-owner flag prevents legacy Ach/Stats writers from also incrementing an owner already included in the PvE outcome transaction; pure capture builders are unaffected.

## Validation scope

The 0.3.13 local run passed **43 Lua suites / 491 named cases**, including 18 strict admission/compaction cases, 22 consumable cases and 21 extended maintenance cases. Those checks exercise actual modules, CAS conflicts, lost acknowledgements, out-of-order concurrent modes, 64-to-four normalization, pending protection and eviction/replay. Lua 5.1 syntax compilation passed for all 59 runtime modules. Reports are in `Design/Release-0.3.13/validation/retention-local/`. These local results do not by themselves establish isolated-network, process-restart, production-deployment or Android-device validation; those have separate release evidence.

Release 0.3.6 additionally passed real Nakama 3.37.0 HTTP/WS tests on a fresh isolated PostgreSQL database: 37 recovery checks with four abrupt restarts of only the verified disposable Nakama container, and 209 multiclient checks. The paid bot Race was genuinely entered, created and joined over WebSocket before process loss; its two-matter refund stayed single after a second restart. Prepared reward and committed-outbox crash-window fixtures were explicitly Console-seeded in that disposable database, then recovered through real RPCs/restarts. Full 25/50-cell bags retained and delivered all queued loot, and repeated protected sales did not sell newly delivered items. See `Design/Release-0.3.6/validation/isolated-{recovery,multiclient}.json`.

All 42 local modules matched the tested 43-file runtime tree (including the existing server bootstrap), SHA-256 `845bc94ed086bd7e858f63347308b9630dd5a0d9d4409d79d17e634211bb2809`. Production deployment used that exact tree after two idle checks and a verified PostgreSQL dump/runtime backup. Post-deployment security smoke passed 25 checks and dashboard smoke passed three. These server tests do not constitute a physical Android device test.

Local Lua 5.1 fault injection runs the actual modules against an atomic CAS storage boundary model, including faults before commit, commit followed by lost acknowledgement, module reconstruction, conflicting workers, another purchase and outbox replay. It does not restart Nakama, call production RPCs, or create paid production matches.

Related suites: `durable_journal_test.lua` (12), `pve_entry_recovery_test.lua` (15), `race_crash_recovery_test.lua` (14), `achievement_outbox_recovery_test.lua` (6), `recovery_service_test.lua` (4), existing Race (37), achievement claim (11), stats (11), inventory/journal integration (6), item-cost guard (5), and actual frozen PvE Rewards/Inventory/Journal integration (14): **135 named cases**, re-run after the main hooks landed. The run records exact source hashes and raw logs in `.utmp/server-recovery/validation/`. All 42 Lua modules also passed Lua 5.1 syntax compilation at that snapshot. These counts are not live-server or process-kill evidence.

An independent actual-core probe additionally passed four cases using the verbatim create RPC and `match_init`: lost create acknowledgement returns the registered match; concurrent create CAS loser returns the same winning match without another debit; ordinary create failure refunds once; a profile CAS conflict uses the fresh affix and energy. The original failure branch incorrectly returned `match_create_failed` when `refund_launch` proved the shared token already belonged to a live match; the coordinating main-module fix returns that match instead. Probe artifacts: `.utmp/expedition/pve-create-core-probe.{lua,json,log}`. This is still a local API-boundary test, not a real Nakama process restart.

The main integration contract is in `.utmp/server-recovery/core-integration.md`; a narrow Race match-ID patch is adjacent. Root owns the PvE frozen reward factory and main hooks; the recovery agent did not edit the main module. A crash before the first durable result intent cannot reconstruct an unpersisted winner or in-memory turn counters; recovery does not invent them.
