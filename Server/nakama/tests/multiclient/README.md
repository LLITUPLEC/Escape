# Многоклиентные проверки Escape

`run.py` управляет независимыми HTTP/WSS-клиентами Nakama. Создаёт только временные
аккаунты `multi_<случайный ID>_<номер>`, использует уникальный `test_group` в
matchmaker query, в `finally` закрывает сокеты, удаляет аккаунты и их записи
рейтингов. Ключи и токены читаются из серверного `secrets/server.yml` и не выводятся.

Тесты арены и обхода платы Race разрешены только на отдельном `localhost:28350`.
Они не запускаются против публичной очереди. Обычный PvP можно проверить против
рабочего HTTPS: дополнительный `test_group` исключает попадание реальных игроков.

На сервере скрипт следует сохранить как `/opt/escape/multiclient_review.py`,
а `isolated_runner.py` — как `/opt/escape/isolated_runner.py`. Из `/opt/escape`:

```sh
python3 multiclient_review.py --scenario pvp --url https://prokrust-play.ru
python3 isolated_runner.py --scenario all
```

Второй вариант создаёт собственный Compose-проект со случайным именем, чистой БД,
портами только `127.0.0.1:28350/28351` и общим лимитом памяти 512 MiB. Нужен запас
не менее 600 MiB доступной памяти. Каталоги копируются через create-only bootstrap
из рабочего runtime; данные игроков не копируются. Параметры Lua pool 4..16
совпадают с рабочим сервером. Перед запуском выполняется `nakama check`.

При наличии `/opt/escape/multiclient-runtime-overlay/*.lua` эти файлы применяются
только к временной копии runtime. Рабочий Nakama не меняется и не перезапускается.
`finally` удаляет только созданные этим запуском контейнеры, сеть, volume, каталог
и одноразовые credentials. JSON-отчёты без токенов сохраняются в `/opt/escape`.

Сценарии: `pvp`, `double-disconnect`, `overlap`, `race`, `arena`, `natural`,
`race-unpaid`, `race-receipts`, `cosmetics`, `all`. `natural` ограничен 150 ходами для каждого classic/pro/Race
и играет до серверного результата, проверяя синхронизацию обоих клиентов.
`race-unpaid` проверяет отказ до создания бота/тикета и отсутствие награды,
не разыгрывая неоплаченный матч. `race-receipts` проверяет повторный вход без
повторной платы, отмену с единственным возвратом, оплаченного бота, запрет возврата
после старта и запрет повторного использования допуска.

`cosmetics` разрешён только в изолированном backend. Проверяет настоящие after-hook
создания аккаунта и привязки e-mail, выбор пола до успешной регистрации и неизменяемость
после неё, отказ в записи закрытого образа и прямых Storage-изменениях, ретроактивное
открытие по серверным достижениям, конкурентный выбор, восстановление после входа
по e-mail и изоляцию двух аккаунтов. Все профили временные, их данные удаляются в `finally`.

`guidance` (также входит в `all`) проверяет новый аккаунт через настоящий auth after-hook,
сохранение завершения/пропуска обучения при конкурентных запросах, отказ устаревшей
сессии и прямой Storage-записи. Для существующего аккаунта без маркера возвращается
`legacy`, повторный вход не включает автоматическое обучение. Условия турниров
проверяются на 0/9/10 победах до списания взноса, три старых представления счётчика
сравниваются через максимум. Проверка Мастерской включает первый рецепт, полный
инвентарь, продажу рецепта и сохранение постоянного признака получения. Данные
прогресса задаёт только Console одноразового стенда; клиентские подделки отвергаются.
Остальные сценарии арены получают десять серверных побед в своей явной фикстуре,
чтобы продолжать проверять турнир, а не останавливаться на новом условии доступа.

`lifecycle` (входит в `all`) проверяет подтверждаемую сдачу через
`duel_match3_forfeit`: конкурентные запросы, одинаковый GAME_OVER обоим клиентам,
окончательное освобождение обоих взносов «Спуска», повтор после удаления матча
и немедленный новый реальный матч. В classic/Pro второй клиент теряет сеть после
matchmaker, но до match_join: оставшийся получает нейтральную отмену не позднее
20 секунд, без победы/XP. Отдельные временные золотые сетки с тремя людьми и пятью
ботами проверяют выход в полуфинал при отключении и при полном отсутствии одного
человека в паре с ботом, с корректными HP. Форма сетки задаётся Console только
одноразовой БД; списание взносов, создание матчей и завершение выполняет настоящий
runtime. Сценарий запрещён на production и любых портах кроме localhost:28350/28351.
Он также отправляет настоящий WebSocket RPC `duel_online_ping_and_count` с payload
`{}` и сверяет `ok/session_epoch`, как проверка связи в клиенте. Оплаченная PvE-вылазка
без единого join завершается без поражения, исходная энергия возвращается один раз,
вооружённый эликсир сохраняется до следующего действительно присоединённого боя.

`double-disconnect` возвращает оба клиента в сохранённые поле и очередь хода.
`overlap` открывает новый сокет до закрытия старого: snapshot должен прийти сразу,
команды старого сокета не должны менять матч, уход старого соединения не должен
удалять новое, а новый сокет должен выполнить реальный ход.

`arena` отправляет восемь HTTP-входов одновременно, проверяет полный турнир и
одновременное завершение разных пар каждого раунда. У каждого участника списывается
ровно один взнос, все результаты сохраняются, финал и повторные poll дают ровно
один приз. Четыре конкурентные доставки прогноза, замена выбора, очистка и повторное
заполнение одной ячейки увеличивают достижение ровно на один; прогноз собственной
пары, неверная сторона, дробный и несуществующий slot отклоняются. Прогноз делает
будущий проигравший четвертьфинала, поэтому приз чемпиона можно сверить с точной
суммой без бонусов прогнозов. Параллельные storage-конфликты дополнительно проверяет
`../arena_concurrency_audit.lua` с управляемым чередованием Lua-coroutine.

`smith` (также входит в `all`) использует восемь временных аккаунтов и новые
правила кузнеца v2. Проверяет цену, отказ доверять клиентской цене/версии,
конкурентную отмену с точным возвратом в полный инвентарь, три раунда и повторные
результаты. Настоящие game-over сообщения содержат компенсацию проигравшего и
слитки/рецепт чемпиона; durable pending сохраняет всё до освобождения места.
`isolated_runner.py --scenario all` и `--scenario smith` передают канонический
`/opt/escape/recovery-item-catalog.json` в одноразовую БД create-only до первого
клиента. Прямой запуск `run.py` для этих сценариев требует `--item-catalog`.

Нарушенные проверяемые инварианты выводятся как `FAIL`. Исключение, оборвавшее
сценарий (например, сеть, ожидание сообщения или несовместимый протокол), выводится
как `ERROR` и требует отдельного разбора; само по себе оно не доказывает дефект игры.
Остальные сценарии продолжаются. Exit code 1 означает неуспешный прогон при наличии
`FAIL` или `ERROR`; JSON сохраняет их отдельно в `checks` и `errors`.
Текущие результаты и ограничения покрытия: `../../MULTICLIENT_REVIEW.md`.

Эти проверки не запускают Unity UI и не заменяют проверку анимаций, экранов,
сцен и платформенных особенностей на нескольких собранных игровых клиентах.

`friends` (входит в `all`) создаёт только два временных друга стенда, проверяет живые входящие socket-уведомления Дуэли/Спуска, принятие/отказ, обе стороны match_ready, правильные правила, начальный roundNumber и отсутствие платы Race за Дуэль. `cosmetics` дополнительно проверяет публичные IDs выбранного аватара, одно долговечное письмо за новое открытие и отсутствие повторной награды при чтении и повторном входе.

`equipment-sets` и `global-boss-practice` входят в `all`, требуют канонический
`--item-catalog` и разрешены только на localhost:28350/28351. Первый проверяет
настоящие character RPC при 7→8→7 частях всех четырёх качеств, равенство статов
ответа и боевого actor, отсутствие бонуса у смешанного качества и реальные
списания 32 рецептов. Второй запускает практику без энергии/телепорта при уже
исчерпанных недельных попытках, защищает armed/bounty/pending данные, сверяет
полный начальный HP, сброс и damage/full-HP знаменатель; отдельно проверяет
сохранение обычной платной попытки на другом временном аккаунте. Изолированный
runner автоматически передаёт каталог обоим сценариям.

`practice-smoke` — отдельная ограниченная проверка после серверного обновления,
которая может работать против рабочего сервера. Создаёт только свой временный
аккаунт и в `finally` удаляет его. Во время трассы Console допускает только GET;
два пробных боя делают обычный ход и завершаются socket OP12. Обычный платный вход,
запись каталога/конфигурации и изменение реального HP не выполняются. До/после
сравниваются все Storage-записи временного игрока **вместе с версиями**, durable
rate budget и системные записи maintenance/event/index/config. Этот сценарий
запускается явно, не входит в `all` и не засеивает канонический каталог.

`harness_equipment_practice_test.py` содержит шесть offline contract-тестов
этих проверок без сетевых вызовов. Реальные HTTP/WebSocket результаты сохраняются
обычным `--report` и оцениваются отдельно.
