# Client recovery and cancellation

The concrete reconnect defect is an ownership epoch change during an ordinary socket replacement. `NakamaBootstrap.EnsureConnectedAsync` called `duel_session_claim` for every new socket of a known email account; that server RPC always increments the epoch. The existing battle retained its earlier owner binding. Surrender used a separate current-session HTTP request, explaining why it remained usable while combat actions failed.

The client now acknowledges ownership once per logical authentication lifetime. Transport replacement and JWT object refresh retain that lifetime. Explicit login, logout, endpoint change and session replacement advance a generation. Delayed recovery/cancellation replies are checked against bootstrap identity, server/account scope, authentication generation, current session and match/transport generation. A successful email authentication already claims ownership and is acknowledged without another claim RPC.

The previous cold-start path only authenticated and displayed the hub; its launch context was in memory. A coordinator now asks the server for a durable active match after initial authentication and returns to `DuelMatch3` with that descriptor. New PvE/multiplayer launch paths check for an existing admission before creating another match. The descriptor restores the actual floor/difficulty, opponent identity and rules; recovery never invokes a paid create RPC. Practice attempts and terminal descriptors are excluded. Pending admissions are retried without charging a new entry.

Socket rejoin is followed by an authoritative checkpoint barrier. The old presentation queue, selected ability and transient FX are discarded, callbacks from the old generation are ignored, and controls remain blocked until a fresh complete board snapshot is applied. Readiness is also checked at packet receive time, before main-thread enqueue, so an old pre-join packet cannot become eligible when the join finishes. The cross-thread flags use volatile reads and the generation changes atomically. The production `ApplyRemoteBoardSync` then calls the existing own/opponent turn methods, which set input and refresh ability controls. Failed sends/rejections request recovery or a checkpoint; actions are never automatically replayed. A transport lease and a pending checkpoint are separate states, avoiding a reconnect loop when the checkpoint itself becomes ready.

Previously the search panel's Cancel called the same forfeit path even during the two-second reveal, while the reveal coroutine could finish and send readiness during the HTTP request. Cancel now freezes/stops that reveal and waits for the correlated create result. PvE and bot-race creates carry one request ID per attempt. Cancellation sends the exact match/admission reference and awaits a terminal server acknowledgement; a missing reference is resolved by a read-only recovery lookup. No blind cancellation or legacy generic race refund is used for an ambiguous operation. A server `battle_already_started`/`cancel_not_allowed` response returns to checkpoint recovery and requires an explicit surrender choice. An unconfirmed or failed refund keeps confirmation pending. A terminal acknowledgement with canonical `refund_recorded=true` may leave after showing a two-second saved-credit notice even if the capped remainder is still pending; this does not pretend that the capped balance has already increased. Full returned progression updates the resource cache; a projection-pending acknowledgement uses the resource read endpoint.

The agreed wire endpoints are `duel_match3_recover` and `duel_match3_cancel`, with `session_epoch` and optional `match_id`/`request_id`. Optional identities are omitted entirely through separate DTO shapes, avoiding JsonUtility converting absent strings into empty properties. Mode is `pve` or `pvp`, with pro/race/boss flags and authoritative opponent metadata. No-ID cancellation is server lookup-only; concrete references are required for an active match or pending paid receipt. Cancellation/refund atomicity, expired lease cleanup and owner rebinding remain authoritative server responsibilities implemented by the server agent.

Validation is split deliberately:

- `ExpeditionReconnectAccountQa.Run`: production recovery/cancel JSON and asynchronous account/session generation boundaries, claim-once gate, cold launch context, terminal/practice exclusion and coordinator retries.
- `ExpeditionBattleReconnectQa.Run`: production rejoin/checkpoint queue, `ApplyRemoteBoardSync`, input lock and ability refresh, actual tile-click swap and ability request after simulated five/30-second transport outages, stale queued callback rejection, pending-create Cancel, reveal readiness suppression, first-action cancellation denial and existing-paid-match recovery.
- `ExpeditionReconnectReleaseQa.RunBatch`: root-owned aggregate with those groups and UI/practice/initial-state regressions. Output is under `.cache/qa/reconnect-0317/`.

Runtime and Editor Roslyn compilation passed before the native aggregate. The aggregate result is recorded separately after the actual run; the offline client fixture does not claim a physical-device airplane-mode test or a real server test. No Unity instance was launched by the client agent, and no version, deployment or Git operation was performed by this work.

The actual native run on 2026-10-28 passed all 44 account/wire/lifetime checks and all 42 battle/checkpoint/input/cancellation checks. Selected reports and compile logs are under `client/`; their source hashes still match the frozen source. The other aggregate battle-entry, startup and practice phases also passed. At this point the full aggregate was waiting for an unrelated dense-number badge padding fix; these client results do not claim that UI group passed. The transport outages are simulated five/30-second intervals, while the methods, payload parsing, tile input, ability selection/request, checkpoint application, cancellation acknowledgements and asynchronous boundaries are production code.
