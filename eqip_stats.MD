## 3. Целевые ограничения баланса (из ТЗ + уточнения)

Обозначения:

- **Тир шахты** T1/T2/T3 = easy / medium / hard (как в коде).
- **Качество** Q1…Q4 = обычное (зелёный) / редкое (синий) / эпическое (фиолет) / легендарное (золото-оранжевый).
- **Монстр 11** = небоссовый бот 11-го этажа **в выбранной сложности** (каталог × множители сложности; после введения «лестницы» — см. **§3.6**).
- **Фул сет** = все 8 слотов заполнены предметами одного тира и качества (если не оговорено иное).
- **Универсальная метрика силы** (согласовано): сравниваем отношение **(effective DPS игрока × effective EHP игрока)** к **(effective DPS монстра × effective EHP монстра)**. Формулы «effective» фиксируются при первой численной подгонке (учёт брони, исцеления, крита — см. симуляцию/скрипт).

### 3.1. Прогресс к боссу: монстр 11, босс 12 и метрика DPS×EHP

Целевые соотношения ниже — по **(effective DPS × effective EHP)** (см. введение к §3). **Крит** у боссов задаётся отдельно (**§3.5**), в эти оценки «силы босса» для игрока **не смешивается** крит босса — он влияет на бой через отдельный проход.

#### Обычный монстр 11 (не босс)

Ориентир на момент **перед боссом 12** (игрок в основном в **эпике**; эпики с рецептов **11-го** монстра + синие):


| Состав / проверка                                                                              | Ориентир по метрике                                                                                              |
| ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **4 эпика** (крафт по рецептам с **монстра 11**) **+ 4 синих + бонусы уровня героя (~11 ур.)** | суммарная сила игрока **≈ 0,60** от силы **босса 12** (**DPS×EHP** в том же тире шахты).                         |
| **Фулл эпик** (8 эпиков в слотах) vs **босс 12**                                               | сила игрока **≈ 0,80** от силы **босса 12** (игрок **слабее** босса по метрике — ориентир **80%** «силы босса»). |
| **Фулл легенда** vs **силу монстра 11**                                                        | **≈ +120%** к силе монстра 11 — ориентир для поздней прокачки; долго играем в **эпике**, это нормально.          |


**Нюанс ×2 у босса:** босс **в 2 раза сильнее** предыдущего обычного (11-го) по **DPS×EHP**. При **фулл эпике ~0,8** от босса возможна **просадка** — **допустимо**: в магазине планируются **зелья** (атака/защита) и **временная экип** (щит с бронёй и т.п.), вне базовых таблиц крафта.

#### Босс 12 и фулл легенда на «своём» тире


| Проверка                                                                              | Условие                                                                                                                                     |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Фулл легендарная экипировка** тира **T1** на **лёгкой** шахте vs **босс 12** лёгкой | игрок **уверенно** сильнее босса; целевой запас **≈ +20%** по стратам (в той же метрике **DPS×EHP**, согласованной с экипировкой).          |
| Аналогично                                                                            | **T2** / средняя шахта, **T3** / сложная — тот же принцип: **легенда своего тира** vs **босс 12** того же тира даёт **~+20%** преимущества. |

Целевые **суммы по первичным статам с экипировки** (HP / урон / броня / лечение) — вилки как раньше:


| Стат     | Вилка (сумма с **8 предметов экипировки**) |
| -------- | ------------------------------------------ |
| Здоровье | ~30 000                                    |
| Урон     | 2 700–3 000                                |
| Броня    | ~2 000                                     |

**Крит (согласовано):** **итоговый шанс крита в бою** (экипировка + база 12 уровня) = **27%**, из них **база уровня 12 = 6%**, значит с **экипировки** нужно **~21%** к криту (при сохранении 6% в Lua — при 5,5% в коде пересчитать долю с вещей).

### 3.3. Иерархия качества и тира (последовательная)

Для **одного слота** действует **сквозная** прогрессия (новое ТЗ):

1. **Зелёный предмет T2** сильнее **легендарного предмета T1** того же слота (по суммарной «силе» слота / метрике).
2. **Зелёный предмет T3** требует при крафте **легендарный предмет T2** того же слота (**§4.2**) — следовательно **зелёный T3** > **легенда T2** при корректных таблицах статов.
3. Внутри одного тира сохраняется цепочка качеств: зелёный → синий → фиолет → легенда (с учётом крафта из **§4.2**).

Старые неравенства вида «фиолет T1 vs зелёный T2» **заменены** этой **последовательной** лестницей; численные таблицы `item_defs` должны проходить монотонность **для каждого слота** (или по норме «силы слота»).

### 3.4. Боссы, «вилка прогрессии» и серверный бафф (**20%**)

**Проблема дизайна:** фиолетовый рецепт и фиолетовый крафт привязаны к **боссу 12**, тогда как **монстр 11** идёт до него — игрок не может быть «в фулл фиолете» до первого убийства 12-го босса. Логика баланса смещается на **предыдущий тир качества + серверный бафф** (и мастерство на поле).

Согласованные **ориентиры** (под метрику §3; бафф зафиксирован **20%** ко всему, **кроме крита**, как ранее оговаривалось):


| Бой                           | Ожидаемая «готовность» (порядок величин)                                                                                                                        |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Босс 8** (любой тир шахты)  | **Полный зелёный сет** соответствующего тира + **серверный бафф 20%** (не крит) → **примерно паритет** с боссом по **DPS×EHP**; исход упирается в игру на поле. |
| **Босс 12** (любой тир шахты) | **Полный синий сет** того же тира + **бафф 20%** → паритет; без фулла синего и без баффа попытка должна ощущаться **бессмысленной** (TTK / ресурсы / вход).     |


Фиолет и легенда — **post-boss-12** прогрессия (фарм материалов, крафт, тессеракты, золотой рецепт), усиливают персонажа для **повторных прохождений**, следующих тиров и контента «потом».

**Бафф в этой итерации не реализуем** — закладываем **цифры боссов** так, чтобы при подключении баффа **20%** паритет из таблицы сохранялся. Численная подгонка должна **согласовать** этот блок с целями **§3.1** (в т.ч. **фулл эпик / фулл легенда vs босс 12**).

### 3.5. Фиксированный шанс крита у боссов (после подбора остальных статов)

После того как зафиксированы HP/урон/броня/лечение боссов, **жёстко задаём `base_crit` у боссов** (в каталоге или оверрайдом на матч):


| Босс        | Лёгкая шахта | Средняя | Сложная |
| ----------- | ------------ | ------- | ------- |
| **Этаж 8**  | 10%          | 20%     | 30%     |
| **Этаж 12** | 15%          | 30%     | 45%     |


Остальные монстры и босс 4 — по общей кривой баланса (без этого жёсткого правила, если не решите иначе).

**Примечание:** при текущей формуле в `match_join` крит бота умножается на `stat_mul`. Если для боссов 8/12 нужны **ровно** проценты из таблицы на всех тирах, возможен **оверрайд крита после скейла** или отдельные поля «крит без множителя» — зафиксировать при реализации.

### 3.6. Средняя / сложная шахта: лестница этажей и стартовый монстр тира

**Босс** относительно предыдущего **небоссового** этажа: **×2 по DPS×EHP** (крит босса — отдельно, **§3.5**).

**Старт следующего тира шахты** (ориентир для каталога ботов):


| Переход               | Сила **монстра 1** нового тира (DPS×EHP)                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------- |
| **Лёгкая → средняя**  | ≈ **1,6×** силы **монстра 11 лёгкой** (то есть **на 60% выше**, чем монстр 11 **предыдущего** тира шахты).     |
| **Средняя → сложная** | ≈ **1,6×** силы **монстра 11 средней** (аналогично: **+60%** к «конечному» обычному монстру предыдущего тира). |


Далее этажи **2…12** внутри тира — **монотонно сильнее** предыдущего.

**Реализация (согласовано): вариант A** — **три подкаталога ботов** (`easy_*`, `medium_*`, `hard_*`), **ручные кривые**. Сервер выбирает набор по `mine_difficulty`. `mine_stat_multiplier` для статов ботов — **1.0** или только для **наград** (без двойного скейла).

Альтернативы **B/C** — запасной план.

## 4. Модель данных экипировки (согласовано)

### 4.1. Идентификация предмета в каталоге

Минимальный состав ключа определения (`def_id`):

- `slot` — один из 8 enum-строк (как в примере `duel_match3_item_catalog.example.json`).
- `tier` — `1 | 2 | 3` (T1–T3; добыча/крафт только в «своей» шахте).
- `quality` — `**normal` | `rare` | `epic` | `legendary`** (в т.ч. для схемы ID).

**Схема ID (утверждена):**  
`eq_t{tier}_{quality}_{slot_short}` → пример `eq_t3_legendary_weapon_r`.

### 4.2. Рецепты и объём контента (96 всего)

На **каждый тир шахты** (T1 / T2 / T3) приходится **32 предмета экипировки** по рецептам: **8 зелёных + 8 синих + 8 фиолетовых + 8 легендарных**.


| Источник рецептов                                         | Количество                                                                 |
| --------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Шахта** (монстры **3 / 7 / 11** и боссы **4 / 8 / 12**) | **72** рецепта (**24 × 3** тира): только зелёный / синий / фиолетовый ряды |
| **Вне шахты** (покупка, обмен, глобальный босс — позже)   | **24** рецепта (**8 × 3**): только **легендарные** золотые                 |
| **Итого в игре**                                          | **96** рецептов (**32 × 3** тира)                                          |


**Шахта — 72 уникальных рецепта** в данных (по тиру). На **каждый тир** **24** рецепта (**8 зелёных + 8 синих + 8 фиолетовых**). Источники разделены: **§4.3**.


| Цвет качества | Пре-босс (этаж) | Босс        |
| ------------- | --------------- | ----------- |
| Зелёный       | монстр **3**    | босс **4**  |
| Синий         | монстр **7**    | босс **8**  |
| Фиолетовый    | монстр **11**   | босс **12** |


**Предмет «рецепт»:** `max_stack = 1` (не стакается). В сундуке до **изучения**.

**Цепочка крафта (материалы и поглощение):**

- Базово: **руда**, **золото**, **знание рецепта**, **слитки цвета качества** (зелёный/синий/фиолетовый предмет — слитки того же цвета; **легендарка** — **тессеракт** вместо слитков).
- **Синий** из зелёного + ресурсы; **фиолет** из синего; **легендарный** из фиолетового того же тира + тессеракт + **золотой рецепт** (вне шахты).

**Доп. требование для зелёного качества на высших тирах шахты** (связь с **§3.3**):


| Крафт                  | Дополнительно к слиткам/руде/золоту                                                                                                                |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Зелёный предмет T2** | **Легендарный предмет T1** в **этом же слоте** — **обязательно поглощается** при успешном крафте (снимается с персонажа/инвентаря и уничтожается). |
| **Зелёный предмет T3** | **Легендарный предмет T2** в **этом же слоте** — **обязательно поглощается** тем же правилом.                                                      |


### 4.3. Дроп рецептов: пре-босс (3 / 7 / 11) и босс (4 / 8 / 12)

Для **каждой тройки (тир шахты, цвет рецепта)** есть **два независимых пула по 4 рецепта** — **фиксированное распределение по слотам** (одинаково для зелёного / синего / фиолетового рядов):


| Пул              | Этаж                 | Слоты (enum / роль)                                                                      |
| ---------------- | -------------------- | ---------------------------------------------------------------------------------------- |
| **A — пре-босс** | монстры **3, 7, 11** | **Helmet** (шлем), **Chest** (тело), **Gloves** (запястья), **WeaponLeft** (левая рука)  |
| **B — босс**     | боссы **4, 8, 12**   | **WeaponRight** (правая рука), **Legs** (ноги), **Shoulders** (плечи), **Feet** (ступни) |


#### Пул A — монстр 3, 7 или 11 (не босс)

1. **25%** — сработало ли **вообще** выпадение рецепта как награды.
2. Если да — выбор среди **ещё не выученных** из этих **4** рецептов: изначально **по 25%** на каждый.
3. Как только один рецепт **выучен** — его шанс **0%**; у оставшихся **трёх** распределить **по ⅓ (~33,33%)** каждый.
4. Когда все **4** выучены — с этого монстра рецепты **не падают**.

#### Пул B — босс 4, 8 или 12

1. **100%** — с награды **выпадает рецепт** (как отдельная награда «типа рецепт»).
2. Распределение по **4** рецептам босс-пула — по той же логике «не выучен → равные доли среди оставшихся», что и в пуле A (после выучивания одного — **0%** ему, **⅓** остальным трём).
3. Когда все **4** боссовских рецепта цвета выучены — босс **не выдаёт** новых рецептов этого пула.

Итого на цвет и тир: **8** рецептов (4+4), на три тира шахты — **72** записи в каталоге.

**Изучение:** рецепт из сундука **изучается** — предмет **пропадает (тратится)**, в мастерской фиксируется знание; крафт предмета по этому знанию **без лимита** по числу крафтов (лимит — только руда/золото/слитки/тессеракт).

### 4.4. Слитки по цвету (расширение с одного вида)

Сейчас в экономике условно один тип слитка — нужно **три цвета**, привязанных к **диапазону этажей** добычи:


| Цвет слитка    | Этажи монстров (внутри выбранного тира шахты) |
| -------------- | --------------------------------------------- |
| **Зелёный**    | **1–4**                                       |
| **Синий**      | **5–8**                                       |
| **Фиолетовый** | **9–12**                                      |


**Шанс выпадения слитка** с обычного монстра (если этаж в диапазоне цвета):


| Этажи              | Шанс     |
| ------------------ | -------- |
| **1, 5, 9**        | **25%**  |
| **2, 6, 10**       | **50%**  |
| **3, 7, 11**       | **75%**  |
| **Боссы 4, 8, 12** | **100%** |


**Босс** даёт **в 2 раза больше** слитков по количеству, чем обычный монстр **на том же этаже** (базовое число в таблице наград ×2 для слитков).

**Стек:** слитки **стакуются до 100** в одной ячейке инвентаря (`max_stack = 100` в `item_defs`).

**Тессеракт** — отдельный предмет; для легендарного крафта **вместо слитков**; источники: **дроп**, **покупка за материю или золото** (**§7.4**).

### 4.5. Отображение в UI (качество и тир)

- **Качество:** фон зелёный / синий / фиолетовый / золото-оранжевый — по полю `quality` из каталога или по соглашению об ID.
- **Тир:** отдельная **иконка предмета** с нужным фоном/рамкой под **качество и тир** (как в тестовых `ItemDefinition` в `Assets/_Project/Data/Character/Items`; детали подключения — отдельно по готовности арта).

### 4.6. PvP: режимы (согласовано)


| Режим                                 | Что входит в статы                                                           | Что **не** входит                                                                                                                |
| ------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **Текущий PvP**                       | Жёстко **150 HP**, остальное 0; **Ярость** даёт динамику урона/крита.        | Экипировка, уровень, **все** серверные баффы PvE.                                                                                |
| **«Три в ряд Pro»** (кнопка на Арене) | **Бонус от уровня** + **бонус от экипировки** (как в PvE по формуле статов). | **Серверный бафф 20%** и **любые PvE-множители** (шахта, сложность мира и т.п.) — **не применяются** ни в обычном PvP, ни в Pro. |


Отдельные **ареновые** множители урона/HP для Pro **не планируются** на первом шаге — только уровень + шмот.

## 5. Распределение статов по слотам (**согласовано**)

Чтобы уложиться в **суммы из §3.2**, зафиксированы **роли слотов** (не все слоты обязаны давать крит и лечение).

Примерный принцип (цифры — для последующей подгонки под симуляцию боя):


| Группа слотов           | HP                         | Броня                 | Урон                          | Лечение  | Крит                      |
| ----------------------- | -------------------------- | --------------------- | ----------------------------- | -------- | ------------------------- |
| Helmet, Chest, Legs     | высокий вклад в HP         | средний               | низкий                        | низкий   | 0–немного                 |
| Shoulders, Feet         | средний HP                 | высокий вклад в броню | низкий                        | низкий   | 0                         |
| Gloves                  | низкий                     | низкий                | средний                       | средний  | заметный                  |
| WeaponLeft, WeaponRight | зависит от типа (см. ниже) | зависит от типа       | **основной урон** или 0 (щит) | 0–низкий | часть крита (если не щит) |


**Слоты оружия (согласовано):**

1. **Два кинжала / два полноценных оружия** — оба слота дают урон (и прочие статы по дизайну).
2. **Щит** — обычно **левая рука** (`WeaponLeft`): **без урона**, уклон в **броню и/или HP**; правая рука — основное оружие.
3. **Двуручное оружие** — занимает **один** слот (логически привязать к «ведущей» руке), **второй оружейный слот пустой и заблокирован** (нельзя надеть второй предмет). На сервере и в UI нужны флаги `two_handed` / пара слотов.

**Крит в бою 27%** (см. §3.2): с экипировки **~21%** при базе 6% — распределить по слотам так, чтобы не было абуза «всё в перчатки» (при необходимости ввести потолок крита на слот).

## 6. Баланс монстров и наград (стратегия обновления каталога)

### 6.1. Что меняем в первую очередь

1. **Кривая угрозы по этажу и тиру** — чтобы выполнить лестницу из **§3.6** и ощущение «средняя не равна просто ×2 всего подряд».
2. **Боссы** — правило «×2 к предыдущему обычному», **фиксированные криты** из **§3.5**, выпад рецептов по **§4.3** (пулы **3/7/11** и **4/8/12**), **цветные слитки** и **×2** слитков с босса — **§4.4**.
3. **Награды XP / золото / руда / материя / ключи** — не ломать прогрессию уровней; при увеличении времени на этаж возможна **лёкая подстройка XP** (только по метрикам «час игры на уровень»).
4. **Стоимость атаки** — сохранить ощущение «дорого на высоких этажах», но согласовать с новым TTK; при необходимости развести **стоимость по тиру** отдельными полями или таблицей.

### 6.2. Связь с экипировкой

После того как зафиксированы **суммарные статы фула** по Q/T для каждого тира, для каждого бота можно задать **целевой TTK / допустимый процент побед** (хотя бы грубо) и подогнать `hp_bonus`, `base_damage`, `base_armor`.

**Аффиксы этажей** (`MINE_AFFIX_POOL`): при **численной подгонке баланса не учитываются** (как будто аффиксов нет). Реализация в игре может остаться; позже при необходимости — отдельный проход по влиянию на TTK.

## 7. Техническая миграция: слитки и рецепты → предметы сундука

### 7.1. Текущее поведение

- `progress.ingots`, `progress.blueprint_*` — скаляры в объекте прогресса PvE.
- Награды с матча отдаются клиенту в payload (`rewardIngots`, `rewardBlueprint`).

### 7.2. Целевое поведение

- **Слитки** — **три цвета** (`ingot_green` / `ingot_blue` / `ingot_purple` или префиксы в `def_id`), `**max_stack = 100`**, тип `**material**`, не экипируются.
- **Рецепт** — предмет `**recipe`**, `**max_stack = 1**` (в инвентаре не стакается), привязка к слоту/качеству/тиру.
- Награды с боя → `**character_sheet.inventory**` / сундук; **изучение** рецепта отдельным действием (предмет рецепта **снимается** с инвентаря, флаг «знание» в данных мастерской).

### 7.3. Серверные задачи (черновик)

1. Расширить `duel_match3_item_defs`: `kind` (`equipment|material|recipe|consumable|tesseract`), `max_stack`, `tier`, `quality`, три вида слитка.
2. В RPC награды за PvE: вместо инкремента `progress.ingots` — `**add_item_to_inventory`**, для слитков — с учётом **стека 100**; таблицы шансов слитков и рецептов — **§4.3–4.4**.
3. Миграция: старые `ingots` → эквивалент в **одном** из цветов или конвертация по правилу (уточнить при релизе); чертежи → предметы-рецепты.
4. **RPC `recipe_learn`** (или аналог): потребить предмет рецепта из сундука → запись в **выученные**; нельзя выучить второй раз тот же `def_id`.
5. **Крафт `workshop_craft`**: проверка **знания** рецепта, **руда**, **золото**, **слитки**; для **зелёного T2/T3** — **поглощение** экипированной или лежащей в инвентаре **легенды T1/T2** того же слота (**§4.2**); **тессеракт** для легендарки; поглощение нижестоящего качества при апгрейде внутри тира.
6. **Учёт выученных**: два подпула по **4** рецепта на (тир, цвет) — **пре-босс** и **босс** (**§4.3**); плюс **24** золотых; логика дропа с **25% / 100%** и пересчётом **25% → ⅓**.
7. Обновить `duel_match3_pve_mine_cost.lua` (или слой над ним): если стоимость атаки когда-либо потребует **предмет из инвентаря**, добавить ветку `item_def_id` + списание стека.
8. **PvP «Три в ряд Pro»**: отдельная ветка `match_init` / режим — `**character_stats_base_for_level` + `sum_equipment_bonuses`**; **не** применять `mine_stat_multiplier`, **не** применять серверный бафф PvE. Обычный PvP без изменений.

### 7.4. Тессеракт (экономика)

- Источники: **дроп** (как сейчас с контента), **покупка за материю или золото** (витрина/обмен — по реализации).
- Вопрос про «**верхний стек**» в инвентаре: имелось в виду **максимум единиц в одной ячейке стека** (`max_stack` в `item_defs`). Для тессеракта задаётся **в каталоге**; отдельный глобальный «потолок по тессерактам» не требуется, если устраивает стек из каталога и размер сетки инвентаря.

### 7.5. Клиент

- `WorkshopScene`: UI крафта, фильтр по тиру/качеству, отображение требований.
- Иконки слитков/рецептов как обычные иконки предметов; **отдельные спрайты по качеству и тиру** (**§4.5**).
- Синхронизация каталога с Nakama (`ItemDefinitionsNakamaImportTool`).

## 8. Мастерская (игровой поток)

1. Рецепты **попадают в сундук** (**96** всего: **72** в шахте, **24** легендарных вне шахты — **§4.2**): пре-босс / босс — **§4.3** (слоты по таблице); золотые — IAP / обмен / глобальный босс / заглушка.
2. Игрок **изучает** рецепт из сундука: предмет **исчезает**, в мастерской появляется возможность **крафтить** соответствующий предмет (**§7.3** `recipe_learn`).
3. Фармит **руду, золото, цветные слитки** (и **тессеракты** для легендарки) в том же тире шахты (**§4.4**).
4. Цепочка качества: **зелёный** → **синий** → **фиолетовый** → **легендарный** (фиолет + тессеракт + золотой рецепт); для **зелёного T2/T3** — **поглощение** **легенды предыдущего тира** в том же слоте (**§4.2**).
5. Сервер валидирует тир, слот, щит/1H/2H, списание материалов и поглощаемый предмет при апгрейде.
6. UI **WorkshopScene**: изучение рецепта, список знаний, крафт, недоступные строки серые (нет ресурса/знания).

## 10. Риски и зависимости

## 13. Эволюция JSON-файлов и storage (кратко)

Да — по мере внедрения плана **примерные** файлы в `Server/nakama/data/` и схемы в Nakama **расширятся**. Ниже — как это стыкуется с **вариантом A** (три кривые сложности).

### `duel_match3_bots_catalog` (и/или три файла)

- **Идея:** для **каждого этажа** и **каждой сложности** задать свои `hp_bonus`, `base_damage`, награды, `cost_attack` и т.д. без «одного `mine_11` на все тиры».
- **Два равноправных варианта хранения:**
  1. **Три файла** (например `..._bots_easy.json`, `..._medium.json`, `..._hard.json`) с одинаковой внутренней структурой и ключами `mine_1`…`mine_12`.
  2. **Один файл** с ключами вроде `**mine_easy_11`**, `**mine_medium_11**`, `**mine_hard_11**` (как вы описали) — тогда сервер при старте боя выбирает ключ по `(difficulty, floor)`.

Оба подхода позволяют **точечно** править, например, только `mine_medium_1` под лестницу **§3.6**. Что именно выбрать — вкусовщина репозитория; в **§14 фаза 0** зафиксировать один стиль.

### `duel_match3_item_catalog` (пример → полный каталог)

- Структура **расширится** полями: `kind` (экип / материал / рецепт / тессеракт), `**max_stack`**, `**tier**`, `**quality**`, опционально **щит / 1H / 2H**, привязка рецепта к слоту.
- В репозитории остаётся **example** как образец; боевой каталог — в Storage Nakama + импорт в Unity.

### `duel_match3_character_sheet` (пример → фактические данные)

### Совместимость id рецептов (каталог ↔ `learned_recipes`)

В каталоге экипа поле **`craft_recipe_id`** задано как **`recipe_drop_t{mine_tier}_{color}_{Slot}`** (например `recipe_drop_t1_green_WeaponRight`). У части аккаунтов в сохранении остались **старые** id без тира **`recipe_drop_{color}_{Slot}`** (например `recipe_drop_green_WeaponRight`). Это **не привязано к одному слоту оружия**: для **всех восьми слотов** T1 (зелёный / синий / фиолетовый) действует одно правило соответствия **t1 ↔ без тира**. Отдельно для **шлемов** T2/T3 зафиксированы пары вида `recipe_drop_t2_green_Helmet` ↔ `recipe_t2_green_Helmet` (и аналог для T3).

**Реализация:** клиент `WorkshopSceneController.IsRecipeLearnedForCraft`; сервер `sheet_has_learned_for_craft` в `duel_match3.lua` (проверка крафта и фильтр «уже выучено» при дропе рецепта из шахты).
